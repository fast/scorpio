# Timer service and handle design

This document records the ownership, scheduling, and benchmark decisions behind Scorpio's timer capability. The public contract remains the API and module documentation.

## Ownership and injection

`TimerService::new()` creates the timer backend; `service.handle()` supplies a cloneable `TimerHandle` to library constructors. The application keeps and drives the service, either in its existing reactor or on an explicitly owned thread. Handles submit operations and observe the clock, but do not own the driver's lifetime or keep timers progressing. No executor context is needed to create or poll a delay. Owning futures can cross a `Send + 'static` task boundary when the wrapped operation can.

A concrete handle is the smallest injection contract for a library that chooses Scorpio. It adds no generic parameter to that library's public types, no dynamic dispatch, and no extra future allocation. Deterministic tests use another real service via `new_at` and `turn`. A separate factory returning Scorpio `Delay` values would still bind the consumer to Scorpio without removing the service lifecycle requirement.

A library that actually supports multiple timer backends can define a narrower deadline capability at its own boundary. An associated future permits static dispatch but propagates a type parameter; a dynamically dispatched factory needs an erased future such as `Pin<Box<dyn Future<Output = Result<(), TimerError>> + Send + 'static>>` and adds an allocation per timer. A generic `timeout<F>` method itself is not dyn-compatible. That abstraction must also define clock, shutdown, and error semantics across backends. Scorpio does not impose those choices before there is a multi-backend consumer. See the [Rust trait rules](https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility).

The names describe the actual boundary: `TimerHandle` is an injected task capability and `TimerService` owns timer state, advancement, and shutdown. `TimerDriver` would also be a valid backend name; it does not require owning a full reactor. `TimerContext` and an aggregate `IoContext` provide no additional capability here. Applications can group a non-optional handle with other dependencies in their own context.

## Consumer boundary: Cache2

[Cache2's I/O engine](https://github.com/scopedb/cache2/blob/d6f4b879043be6eb07839eb3cc9e75f0856ef35b/cache2/src/io/engine/mod.rs) illustrates the required behavior. Read admission calls `timeout_at` on an owned semaphore acquisition. The foreground admission wait and submitted I/O have separate budgets: submission establishes a new completion deadline. An in-flight read uses that absolute deadline, requests cancellation when it expires, and then applies a relative cancellation grace period to the same borrowed I/O request. Its guard cancels an abandoned request while the engine retains resources needed by unfinished I/O. Replacing a timeout must preserve that ownership; it must not resubmit the request or imply that dropping a timer cancels kernel I/O.

A Scorpio integration can store a `TimerHandle` in the cache and pass references down this path. `timer.timeout_at(deadline, request.request_mut())` preserves the borrowed request for a subsequent `timer.timeout(cancel_grace, request.request_mut())`. `TimeoutError::Closed` must be mapped as an unavailable timing service, separately from `Elapsed`; the request still needs its normal cancellation and resource cleanup. An absolute deadline can be shared across stages without resetting the time budget. The guarded future is polled first, matching Tokio's ready-operation precedence; neither timeout can preempt a poll that does not yield.

At that snapshot Cache2 requires Tokio 1.53.1 with `rt` and `time`, has a Rust 1.98 MSRV, and retains a Tokio handle for `spawn_blocking` during open and close. Timer injection alone therefore does not make Cache2 independent of Tokio. Its background append/reclaim and I/O workers already have separate blocking-thread lifecycles. That broader execution boundary belongs to a Cache2 change, not this timer API.

## Shared service lifecycle

One service created by application startup can serve libraries on multiple executors. The [shared timer example](../examples/src/shared_timer.rs) keeps the thread, stop signal, and join handle in application state. Its clients receive only `TimerHandle`. The [custom reactor example](../examples/src/custom_reactor.rs) instead drives a root future and the timer service on the caller's thread. Both use the same `turn` / `prepare_wait` protocol and a latched wake, so a notification just before parking is retained.

There is no built-in global service, thread-spawning constructor, or feature that silently enables one. A static singleton generally lives until process exit, complicates shutdown and test isolation, and cannot express which application or runtime owns the driver. Applications may still deliberately publish a handle through their own global state, while retaining an explicit owner and shutdown policy. Creating a handle never creates a hidden thread. No feature flag is needed for the crate's only current capability.

A live but undriven service cannot distinguish a stalled driver from one that has not yet been scheduled; a liveness Boolean would give false assurance. Submitted timers remain pending until `turn` or service drop. Dropping the service wakes waiters with closure errors even when handle clones survive. Applications should stop or drain dependent library work before shutting down their timer owner. A first poll of an already elapsed deadline may complete immediately; see the `Delay` contract.

Avoiding a built-in thread also keeps the integration policy out of target selection, but does not by itself provide browser support: Scorpio currently uses `std::time::Instant` and has no browser clock/wait adapter. The thread example targets native platforms; [Rust's `wasm32-unknown-unknown` guidance](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html) documents the limitations of `std`. A browser integration needs an explicit clock and event-loop design before support can be claimed.

## Timing wheel

The wheel uses six radix levels with 64 slots each and a one-millisecond base tick. It covers `2^36` milliseconds (about 795 days) before an ordered overflow tier is needed. Future deadlines are rounded up, never down, and upper-level entries that are not yet due cascade toward level zero; entries already due can fire directly from their current level.

Every slot is an intrusive doubly linked list backed by a slab, so insertion and cancellation are constant-time once an entry's slot is known. A 64-bit occupancy bitmap per level makes empty-slot discovery cheap, and a selected slot remains cached while a bounded turn drains it.

Registrations and cancellations arrive through a mutex-protected multi-producer queue with reusable `VecDeque` storage. Producers hold the mutex only long enough to append an operation, while the single-writer timer backend swaps a bounded batch into private scratch storage before touching the wheel. Queue state and the replaceable reactor waker share that mutex, so wake registration cannot race an empty-to-nonempty transition and no separate fence protocol is required. `TimerService::prepare_wait` combines that wake handshake with the next wheel deadline and returns one `WaitPlan`, preventing integrations from observing the deadline and arming the wake in the wrong order. `TurnBudget` bounds both operation messages and wheel entries per turn, and alternation between immediate and non-immediate entries prevents either class from monopolizing a reactor. Wakers are always invoked outside queue and wheel mutation paths.

The task-facing handle is one shared pointer. Its shared allocation contains the operation queue, clock observation, and close state, so cloning a handle performs one reference-count update. Each delay stores its waker inline in the existing `Arc<TimerState>` allocation. A private three-state ownership cell distinguishes a ready slot, a polling task replacing the waker, and terminal ownership. The terminal publisher performs one atomic transition and never waits: it either takes a ready waker or leaves an in-progress polling task to discard the replacement and observe the already-published lifecycle state. The inline slot does not invoke waker callbacks while transferring its exclusive ownership. Queue wake registration reuses an equivalent borrowed waker; a replacement is cloned under the queue mutex and the old waker is dropped after unlocking. Executor waker operations are expected not to panic; arbitrary callback panic recovery is not a supported integration contract. A non-owning data/vtable identity lets repeated polls with the same raw waker identity skip cloning and replacement; semantically equivalent wakers with different raw representations are safely republished. This removes the separate per-delay waker allocation and the former fence pair without adding a general-purpose channel or atomic-waker dependency.

## Source comparisons

- [Linux timer wheel](https://github.com/torvalds/linux/blob/db2ddb87143519e20a95aa36c60b36107b736a58/kernel/time/timer.c) contributes the intrusive bucket, occupancy bitmap, rounded-up deadline, and timeout-oriented batching ideas. The current kernel wheel deliberately avoids cascading and accepts coarser upper levels because most kernel timeout timers are cancelled before expiry. Scorpio does not copy that semantic tradeoff: general-purpose delays and intervals retain one-millisecond, never-early scheduling across the wheel.
- [Netty `HashedWheelTimer`](https://github.com/netty/netty/blob/540c9781f900b21c06e957bceb3d490daa3f0759/common/src/main/java/io/netty/util/HashedWheelTimer.java) contributes the producer queue, delayed cancellation, intrusive buckets, and bounded transfer pattern. Scorpio leaves worker-thread creation and sharing policy to the application; a single explicitly owned service can still be shared by many libraries.
- Boost.Asio's [`execution_context`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/execution_context.hpp), [`io_context`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/io_context.hpp), [`basic_waitable_timer`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/basic_waitable_timer.hpp), [`deadline_timer_service`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/detail/deadline_timer_service.hpp), [`timer_queue`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/detail/timer_queue.hpp), and [`timer_scheduler`](https://github.com/boostorg/asio/blob/4fa4abee89a62fdeeccac2585caece625f40647e/include/boost/asio/detail/timer_scheduler_fwd.hpp) motivate explicit capability association, the `TimerService` name, earliest-deadline reactor interruption, and deterministic shutdown. The selected scheduler is platform-dependent and is commonly a reactor, but the boundary is what matters here: Scorpio exposes the timer-specific owner and its task-facing capability, folds queue advancement into that service, leaves waiting to the application reactor, uses a hierarchical wheel rather than a binary heap, and returns futures rather than dispatching callbacks from a context-owned run loop.
- [Tokio's runtime driver](https://github.com/tokio-rs/tokio/blob/tokio-1.53.1/tokio/src/runtime/driver.rs) and [timer wheel](https://github.com/tokio-rs/tokio/tree/tokio-1.53.1/tokio/src/runtime/time) validate the internal driver/handle split, six-level radix geometry, intrusive entries, and careful racing-reset protocol. Tokio aggregates handles because it owns the full runtime and discovers the current scheduler implicitly. Scorpio does not store or discover a scheduler handle in timer futures; every `Delay` is created from a caller-supplied `TimerHandle`.
- [`async-io`](https://github.com/smol-rs/async-io/blob/576b470ca3cadefdec8b169279df23c9a0a63495/src/lib.rs) and [`futures-timer`](https://github.com/async-rs/futures-timer/blob/e8d2e877147bcdbe5b64c0fbf5df1f2dce1c4253/src/native/timer.rs) provide useful public-API benchmark comparisons, but both use a global fallback and lazily start a helper thread. Those ownership choices are intentionally outside Scorpio's contract.

## Performance regression suite

Run `cargo x bench --quick` for an isolated-process, single-iteration smoke check. Without a filter, the xtask launches each implementation family in a fresh process so async-io and futures-timer helper threads cannot leak into another implementation's samples. Add a name filter such as `cargo x bench expire_registered` for focused Divan measurements where that isolation is not required. Run the same filtered command on both revisions for before/after comparisons, keeping the machine, power mode, toolchain, and background load fixed.

The `timer/frontend_lifecycle` group measures the relative-delay create, first-poll, and drop boundary for Scorpio, Tokio, async-io, and futures-timer at 64 and 1,024 timers. It does not claim that background or service-side work is part of that boundary. Each implementation performs one untimed warmup so the comparison covers steady-state driver and queue storage rather than mixing Scorpio's first queue allocation with reused or global drivers. Divan creates and warms a fresh boxed Scorpio service outside each measured iteration, so moving the service's inline wheel into deferred validation is pointer-sized rather than benchmarked work. Deferred output destruction then drains a count-bounded operation batch and verifies that no deadline remains, also outside the measured interval.

The `timer/scorpio_service` group separately measures registration and cancellation queue draining, which is work that Scorpio deliberately exposes to the application-owned reactor. Its service inputs are boxed outside the timed closure for the same reason. Deferred validators prove that every declared item was registered or cancelled and that no deadline remains, without adding validation work to the measured interval. Keeping this group separate prevents a cross-implementation benchmark from mixing caller latency with asynchronously deferred backend work.

The `timer/expire_registered` group excludes setup and measures Scorpio's direct service turn plus terminal polling. Same-deadline cases cover a single bucket, while mixed-level cases drain already-due entries from multiple buckets and levels. Both advance directly to the final deadline; they do not measure migration of not-yet-due entries between levels. Each service input is constructed, measured, and dropped alone, and the driven clock avoids wall-clock sleeping.

These results are regression and tradeoff evidence, not a universal ranking. The compared crates make different ownership, executor, precision, and background-thread choices; benchmark names keep those paths separate rather than claiming identical semantics.
